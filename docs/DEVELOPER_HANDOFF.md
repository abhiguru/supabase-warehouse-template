# Contributor guide

Orientation for changing this backend. Operator instructions are in [OPERATOR_INSTALL.md](OPERATOR_INSTALL.md); the README quickstart is the entry point for a new installation.

## Repository layout

- `setup.sh`, `start.sh`, `stop.sh`, `rotate-keys.sh` — operator commands; each takes the per-state lock (`scripts/operator-lock.sh`) before touching Docker. `health-check.sh` keeps its name but takes no lock: it is a thin wrapper over `node scripts/watch.mjs health` (the one health check, also used by `doctor --local`) that adds diagnostics.
- `scripts/` — `configure.mjs` (state and config generation), `doctor.mjs` (host preflight, local and external checks), `migrate.sh` + `migration-plan.mjs` (checksummed ledger), `backup.sh` / `verify-restore.sh` / `restore.sh`, `backup-usb.sh` (automatic copy to an enrolled USB drive; see below) and `usb-backup-status.mjs` (its doctor warning), `restore-host.sh` (rebuild a lost host from a backup), `tunnel.sh` (tunnel credential in the state, its systemd unit), `data-fingerprint.sh` (before/after restore comparison), `rotate-keys.mjs` + `keys.mjs`, `compose.sh` (project-owned Compose wrapper; it leaves the `lan` profile out of a command while the host does not have the LAN address, and hands Compose `WAREHOUSE_MAINTENANCE=upgrading` while the marker `config/maintenance` exists), `maintenance.sh` (`on`, `off`, `status`: closes the API to phones with a 503 `upgrading` answer from both gateways; `upgrade.sh` uses it around the backup and setup; [OPERATOR_INSTALL.md](OPERATOR_INSTALL.md#rerun-and-upgrade), "While it upgrades"), `lan.sh` + `lan.mjs` + `lan-common.mjs` (the optional LAN fallback: `gateway-lan`, the gateway's own image running a plain-http server on the host's private address; `lan.sh start` is the step `start.sh`, `setup.sh` and `restore.sh` use so that a fault of the fallback never stops them; [OPERATOR_INSTALL.md](OPERATOR_INSTALL.md#lan-fallback-plain-http-on-the-warehouse-network), tests `lan-switch`, `lan-url`, `gateway-nginx`), `check-mobile-contract.mjs`. The CI-only drivers (`gateway-smoke.mjs`, `gateway-dns-check.sh`, `load-smoke.mjs`, `recovery-check.sh`, `cups-check.sh`, `sensor-bridge-check.sh`, `pooler-check.sh`) live in `tests/`, with their `npm run test:*` names.
- `migrations/` — numbered SQL applied in order. `functions/` — Deno edge functions. `docker/` — Compose files and digest-pinned image recipes; `docker/nginx/` is the gateway (plain nginx: its configuration files, the two templates that take the origin and the API keys, and the recipe; [CONTAINER_SECURITY.md](CONTAINER_SECURITY.md#gateway-limits-and-routes)); `docker/sensor-bridge/` is the Python Tapo sensor bridge, licensed GPL-3.0-or-later (its own `LICENSE`): the one directory of original code that is not MIT. `deploy/` — the cloudflared config example.
- `scripts/set-capability.mjs <sensors|printing> <on|off>` — edits one flag of `<state>/public/instance.json` atomically (the app's capabilities); afterwards restart `functions` and take a backup (`db:restore` refuses a backup with a different manifest).
- `tests/` — node tests (`*.test.mjs`), SQL tests run by `tests/migrations.sh`, and HTTP drivers for a live instance. The CI install job runs four of them: `operator-api-core.mjs`, `operator-api-final.mjs`, `operator-api-rotation.mjs` (`npm run test:rotation`) and `operator-api-restore.mjs`, all through `operator-fixture.mjs`. Pending, rejected and disabled sign-in, OTP expiry and staff documents are covered in CI by the SQL tests.

## Running checks

- `npm ci && npm test` — node unit tests. The ones that need Docker skip with a message on a machine without it (CI has it): `tests/gateway-nginx.test.mjs` builds `docker/nginx` and runs it against stand-in upstreams (about 10 s; it pulls the pinned nginx image once), and the Compose rendering tests need `docker compose`.
- `bash tests/migrations.sh` — applies every migration twice to a disposable, network-isolated container of the database image (`postgres:18`, the pin printed by `scripts/db-image.sh`) (the second pass must skip unchanged files) and runs the SQL tests. Needs Docker.
- Shell syntax is checked by `npm test` (`tests/shell-syntax.test.mjs`); there is no separate CI step.
- `node scripts/check-mobile-contract.mjs <mobile checkout>` — static name inventory against the app (needs the app's `node_modules`); the pin it runs against is described in [CONTRIBUTING.md](../CONTRIBUTING.md#mobile-companion-pin-mobile_ref). The `contract` job also runs `tests/rpc-callers.test.mjs` with `MOBILE_CHECKOUT` set, which compares the app's RPC names with `tests/rpc_callers_exist.sql`.
- Sensor bridge: `cd docker/sensor-bridge && python3 -m unittest discover -s tests -t .` (Python 3.15 with `requirements.txt` installed; CI job `bridge`), and `npm run test:sensors` on an installed state (builds the image; `--check-config` must exit 0 with fictional values and 78 without; the unit tests run inside the image). Without `docker/sensor-bridge/Dockerfile` it fails.
- Everything else (`npm run test:gateway`, `test:rotation`, `test:anon-timeout` (the 3 s limit of `anon` through PostgREST), `db:backup`, ...) needs an installed operator state; CI exercises them in the `operator-install` job.

## Backup key, signing and the restore verifier

- `scripts/backup-key.sh` (sourced) is the one place for the key and the crypto. The key is `<state>/config/backup.key` (64 hex, 0600), created by `configure.mjs` (fresh setup, and a rerun on a state without one) or by the first `backup.sh`. It is never copied into a backup. `WAREHOUSE_BACKUP_KEY_FILE` overrides the path for verification.
- `backup_hmac` is HMAC-SHA256 built from `sha256sum` and shell builtins, so the key never appears in a process argument list (`openssl dgst -hmac KEY` would show it in `ps`) and the script does not need Node, which is not on the PATH of the systemd unit. The tests sign fixtures with Node's `crypto` (`tests/backup-test-helpers.mjs` `hmacHex`), so the two implementations check each other. Every use has its own label (`warehouse-backup-manifest-v1`, `-archive-v1`, `-encryption-v1`, `warehouse-usb-enrolment-v1`).
- Format **v5** = v4 plus `SHA256SUMS.hmac`. `backup_authenticate DIR ALLOW` runs before anything in a backup is parsed: `sha256sum -c`, then the HMAC, then "the files present are exactly the files listed". A present-but-wrong signature is refused even with `--allow-unsigned`; a missing signature or a missing key is accepted only with it, with a banner on stderr. The flag is only for a lost key. `verify-restore.sh`, `restore.sh` and `restore-host.sh` accept formats v5 and v6 (`backup_check_format` in `scripts/backup-image.sh`, which sets `BACKUP_FORMAT`) and refuse any other label ("Refusing: backup format 'warehouse-backup-vN' is no longer supported; take a new backup with this version (only warehouse-backup-v5 and -v6 are accepted)") before the signature is checked; the label is read before it is authenticated, which is safe because a refusal trusts nothing. A **v5 or v6** backup (`format=` in `metadata.txt`) whose signature file is missing is refused even with the flag while the key (`backup_key_path`) exists, before any checksum is run. The rule is in `backup_authenticate`.
- Format **v6** (since the release that added `rsync` as a prerequisite) = v5 with the object storage as a tree. `scripts/backup.sh`: the link base is chosen first (newest backup in `config/backups-verified.list` that was verified within the last two days and has `storage.manifest`; else the newest v6 beside the new backup that authenticates, verified or not; else none; the list is written only by `watch.mjs prune-backups --verified` and by `watch.mjs record-verified NAME [SECONDS]` (which `upgrade.sh` calls for the backup it has just proved), one `name epoch` line per backup, with a third field, the seconds its verify took, when the writer knew it (every reader takes the first two fields), atomically, mode 0600, read by `backup.sh`, `pruneBackups` and the upgrade preflight, and may not exist), and a candidate is used only if it is on the filesystem of the new backup, is not named in `config/link-base-rejected`, and passes `BACKUP_TREE=skip backup_authenticate` (signature, SHA256SUMS, manifest; not the photos): a failing one is named in a `Warning:` and the next is tried. Pass 1 (`rsync -rptX --link-dest=<base>/storage` into `storage-pass1/`, API up), then the stop (`pg_dump`, integrity, roles, catalog, pass 2, a dry run of the same command that must print nothing, restart). **Pass 2 goes into a new `storage/` with `--link-dest=storage-pass1 --link-dest=<base>/storage`, never into pass 1's directory:** rsync does not consult `--link-dest` for a destination file that exists, and for one whose size and time match but whose extended attributes or mode differ it calls `lsetxattr`/`chmod` on the existing path, which for a hard link changes the base's file and every older backup's (`tests/backup-storage.test.mjs` shows both sides of that with rsync alone). A fresh destination links what matches and creates anew what differs. With the API up again: `storage-pass1/` is removed (so link counts mean "backups sharing"), then `storage.manifest` (`find -printf '%P\0' | sort -z | xargs -0 sha256sum --`, inside `storage/`; a file that cannot be read is left out by sha256sum and found by comparing with the file list), the **rot check**, `metadata.txt` (`link_base=`, `storage_files=`, `storage_bytes=`, `storage_new_bytes=` = bytes of files with link count 1, `rot_repaired=` and `rot_repaired_file=` lines, `stop_seconds=`, `duration_seconds=`), `SHA256SUMS` (lists `storage.manifest`, not the tree), the signature, `chmod` with `storage/` pruned, `mv`. Rot check: a file with link count above 1 is shared with the base; if its hash differs from the base manifest's line (the base manifest is trusted, the base passed its signature check), is not listed there, or could not be read, it is unlinked from the stage only, copied again from the live storage (`rsync -ptX --files-from`), hashed again and must equal the base manifest's line, with its attributes complete (a dry run); then the stage's manifest takes the fresh lines, the backup records `rot_repaired=N` and prints `WARNING: N files re-copied: backup <base> has a damaged copy.` as the last line on standard error, which `watch-daily.sh` passes to `watch.mjs` as `backup_warning=` (daily message and status line; the pass stays ok). If the live copy is missing, unreadable, or differs from the recorded line, the night fails, naming the files, and a live file that differs additionally puts the base's name in `config/link-base-rejected` so the next night copies everything. Invariants: nothing writes into `storage/` of an existing backup (files are shared by hard link; a chmod, touch, setfattr or edit of one changes every backup that links it), and the live `data/storage` is never hard-linked to a backup (restores copy). `backup_authenticate` is in tree mode when the signed list names `storage.manifest`: the present-versus-listed comparison leaves `./storage/` out, and `backup_check_tree` requires the tree to hold exactly the manifest's paths and `sha256sum -c`s them (the manifest passes the same path-safety regexes as `SHA256SUMS`; `BACKUP_TREE=skip`, set by `verify-restore.sh --no-storage-tree`, checks only the chain). After authentication `backup_check_layout` refuses a label that disagrees with the signed list. `restore.sh` authenticates with `BACKUP_TREE=skip` and leaves the hashing to the `verify-restore.sh` it runs next.
- **Free-space preflight and prune protection (`scripts/backup.sh`, `scripts/watch.mjs`).** After the link base is chosen, the DB health and image pin checks and the unsafe-entry check, and before pass 1 and the stop loop (nothing before it stops a service), `backup.sh` computes `need` and refuses when `avail < need + WAREHOUSE_BACKUP_RESERVE_MB` MiB (default 2048, whole number, `10#` against octal; a bad value refuses). With a base: `need = 2 x delta + dump + 256 MiB`, `delta` = "Total transferred file size" of a dry run of pass 1 (`rsync -n --stats`, `LC_ALL=C`, exit 0 or 24 accepted) plus 4096 x the `dir:` count of the same statistics. With no base, or when the dry run fails (then `du -sb` of the tree stands in for the new files): `need = tree + tree/10 + dump + 256 MiB`. `dump` = 1.5 x max(64 MiB, size of the base's `database.dump`); with no base, `pg_database_size`. A figure that cannot be read counts as 0 (the 64 MiB floor stays), except the free space: `df -B1 --output=avail -- <parent>`, else `stat -f -c '%a %S' -- <parent>` (free blocks for a non-root user x block size), else a refusal (`Refusing: could not read the free space of <parent> (df and stat -f both failed) ... Nothing was stopped.`); when `stat -f` stood in, a `WARNING: df gave no free space for <parent>, so stat -f was used ...` line is printed, which `watch-daily.sh` passes on as part of `backup_warning` (joined with the rot sentence by `; `). The refusal is the last line on standard error; `put` and `writeJobStatus` cut at 400 characters. `metadata.txt` carries `preflight_need_mb=` and `preflight_avail_mb=` (signed with the rest). Tests: `tests/backup-storage.test.mjs` ("free-space preflight"; PATH shims for `df`, `stat -f` and `rsync` that pin the arguments and log the calls, so a refusal can be shown to precede pass 1). `pruneBackups` keeps, on top of the newest 7: the path just made, the newest listed backup that is this installation's (`instance.json` matches, `metadata.txt` present, a real directory), and the backup named by `readUpgradeRecord(state).backup` (`scripts/upgrade-record.mjs`; `upgrade.sh` records the verified pre-upgrade backup there and refuses to resume without it); and, for 60 days after its own date, the newest verified backup of each distinct `migration_fingerprint=` in `integrity.txt` (the copy from before each schema change; `LIMITS.keepMigrationStateMs`). `checkRestoreSpace` (alert `restore_space_low`, repeating every 24 hours through the result's `repeatHours`, not the 4 hours of the others) compares the free space of `data/` with the newest verified backup's `storage_bytes` plus the size of its `database.dump` plus 1 GiB (`restore.sh`'s rule, plus the replay of the dump; the upgrade preflight uses the same sum). A doomed backup is renamed to `.warehouse-backup-removing.<name>` first (atomic), its directories get `u+rwx` (`find ... -exec chmod`), then it is removed; leftovers of that name are finished at the start of each prune. A missing `backups/` folder is not an error. `prune-backups` writes argument errors to standard error and treats a bad `--verified` name as a note.
- The Storage service keeps each file's content type and cache control in the extended attributes `user.supabase.content-type` and `user.supabase.cache-control` (storage-api v1.80.2, `dist/storage/backend/file.js`; `user.supabase.etag` only for parts of a multipart upload). rsync `-X` and `tar --xattrs --xattrs-include='user.*'` keep them. v5 backups (and every restore before v6) lost them; `scripts/retag-storage-metadata.cjs` sets them again from `storage.objects.metadata` with the `fs-xattr` module of the storage image (the same one the service uses), through `scripts/storage-retag.sh` / `npm run storage:retag`. After every restore (v5 or v6, so also through `restore-host.sh`), `restore.sh` runs `storage-retag.sh --if-missing`: `retag-storage-metadata.cjs probe` (run as `node -e SCRIPT probe` in the storage container) looks at up to 20 catalogued files spread over the catalog and exits 10 if any has no content type, and only then the full run follows; a failure of either is a warning. This covers v5 backups, v6 backups of files that had lost their attributes, and USB archives written before the archive form keeps attributes. A retag changes the attributes of every live file, and `--link-dest` compares attributes under `-X`, so the next backup copies every photo again. CI's operator-install job runs the real thing against the real storage image after the in-place restore drill (strips the content type from every restored file with `setfattr -x`, then `storage:retag -- --if-missing` must find it and set it again, and a second run must change nothing); the unit tests stand `fs-xattr` in. Tests that need attributes use `setfattr`/`getfattr` (package `attr`) or python3 and skip where the temporary directory refuses `user.*` attributes (`xattrSkip()` in `tests/backup-test-helpers.mjs`).
- `verify-restore.sh` creates its databases from **template0**. A session attached to template1 right after start-up failed `createdb -T template1` in CI on 2026-10-09 ("source database template1 is being accessed by other users"); the likely owner was a background-worker launcher of the earlier database image (the official image has none). template0 accepts no connections, so the race cannot occur; `restore.sh` uses it for the same reason. The dump is self-contained, so nothing from template1 is needed.
- The verifier sizes its data directory from the dumps (factor 10, WAL allowance, floor 768 MiB), uses tmpfs when `MemAvailable` covers it and otherwise a directory under the state that the image itself empties afterwards (PostgreSQL's files belong to the container's user). On failure it saves `docker logs`, the container state and `pg_stat_activity` under `<state>/diagnostics/` before removing the container.
- Real-container coverage without an installed stack: `tests/verify-restore-drill.sh`, run at the end of `tests/migrations.sh`, dumps the migration test database into a signed v5 fixture and runs the verifier twice, once with a session held on template1 and once disk-backed, then once more on a v6 fixture (a `storage/` tree and `storage.manifest`), which must verify and must be refused when a tree file differs from the manifest. `WAREHOUSE_DRILL_KEEP=1` keeps the fixture.
- **Not verified on real containers:** any restore from an encrypted archive.
- Database passwords are one per login since 2026-10-18 (TW-BE-002; [CONTAINER_SECURITY.md](CONTAINER_SECURITY.md#database-passwords-one-per-login)). The list of service logins is `DB_ROLE_LOGINS` in `scripts/db-roles.mjs`. `SECRET_KEY_BASE` and `VAULT_ENC_KEY` exist only after `bash scripts/pooler.sh on` and have no rotation script; the operator guide says so.

## USB backup drive

The operator attaches an **existing exFAT USB drive** and the system does the rest. exFAT because the install may run on Linux or in the Linux VM of a Windows host, and a restore must work on either; the drive is never partitioned or formatted, so existing files on it stay untouched. Archives are signed with the backup key (next section) and **encrypted by default** (`WAREHOUSE_BACKUP_ENCRYPT=0` in the unit only when the operator typed `setup --no-encrypt`; the conf keeps `ENCRYPT_SET=typed|default` so an installation set up before this default, whose stored `ENCRYPT=no` was never a choice, is switched at its next setup with a printed notice). Readable archives let anyone holding the drive read every credential in `compose.env`. Because a lost key makes the encrypted archives unrecoverable, `config/backup-key.escrow` (written by `scripts/backup-key-escrow.sh`: a fingerprint of the key, never the key) must match the key before a drive is enrolled and before an encrypted run writes. Each run copies only the newest verified backup as one self-contained archive (`scripts/backup-archive.sh`), keeps the newest `KEEP` (default 3) valid archives, and deletes the readable archives of this installation once an encrypted one is written and verified. A drive kept on site does not close the off-host custody gate in [PRODUCTION_DEPENDENCIES.md](PRODUCTION_DEPENDENCIES.md); rotating it to another location does.

`scripts/backup-usb.sh` automates it. Layout and trust boundaries:

- **Root, installed once** by `sudo bash scripts/backup-usb.sh setup --state DIR --enroll /dev/sdX1`: copies the script itself to `/usr/local/libexec/warehouse-usb-backup` (root-owned, so root never runs code from the user-writable checkout; setup refuses a group/world-writable script), writes `/etc/warehouse-usb-backup.conf` (state, checkout, user, uid/gid, options), `/etc/warehouse-usb-backup.drives` (root-only, 0600: one `<filesystem UUID> <partition UUID>` line per enrolled drive), a udev rule with one line per enrolled UUID (`ID_BUS==usb`, `ID_FS_TYPE==exfat`) that adds `SYSTEMD_WANTS=warehouse-usb-backup@%k.service`, the template unit, and a scan service + daily timer (enabled only with `--daily`). A rerun keeps `DAILY`, `FRESH_BACKUP` and `ENCRYPT` from the existing conf unless an option names another value (`--no-daily`, `--fresh-backup`, `--no-encrypt`). `enroll`, `uninstall` and `status` complete the set.
- **The unit** runs `ExecStartPre=+helper mount %I` (root: re-checks USB/exFAT/enrolled, waits a few seconds for a desktop automount and uses it, otherwise mounts privately under `/run/warehouse-usb-backup/` with `uid/gid`, `fmask=0177`, `dmask=0077`, `nosuid,nodev,noexec`), then `ExecStart=bash <checkout>/scripts/backup-usb.sh run --device %I` **as the installation user**, then `ExecStopPost=+helper unmount %I` (always, also after a failure: `sync`, unmount every mount of the enrolled drive). The checkout path is baked into the unit: run setup again after moving or updating the checkout (`status` compares the helper with the checkout).
- **Enrolment** is not the exFAT volume serial (32 bits, settable with `mkfs.exfat -i`). `enroll` (root, from the checkout) writes `warehouse-backups/.drive-enrolment` onto the drive: `hmac=` is `backup_hmac(key, "warehouse-usb-enrolment-v1", "<fs uuid>\n<partuuid>\n<instance id>\n")`. `mount` (root helper) accepts only an exact `UUID PARTUUID` line of the root-only list; `run` cannot read that list and instead recomputes the marker HMAC for the drive it sees, before the fresh backup. A bare-serial line left by an earlier release is refused with a re-enrol message; because `run` never starts for it, the helper records that refusal itself in `usb-backup.last` (through `setpriv`, as the installation user, with the internal `refused` subcommand), and `setup` does the same for every such line it finds, so `status` and doctor show it at once. The udev rule still names the serial (world-readable): it only starts the unit, and a forged drive then fails the marker check with nothing copied.
- **`run`** (installation user): refuses root, unenrolled/non-USB/non-exFAT/read-only drives, an unmounted drive, a mount on the data device, and a folder whose `.instance-id` belongs to another instance; with encryption on it also refuses until `backup_escrow_ok` (nothing is written, no fresh backup is taken). It takes a fresh backup (`scripts/backup.sh`, which takes the operator lock itself; it waits up to 15 minutes for the lock) only when the newest verified local backup (`config/backups-verified.list` if PR2's verified list exists, else the newest signed one) is 20 hours old or more. Then, holding the lock, it copies only the newest verified backup (an older one only if that fails its own `backup_authenticate`, which reads the whole tree): `backup_archive_write` (a pax tar of the backup folder, small files first and the `storage/` tree last, hard links dereferenced, `user.*` attributes kept, through `backup_encrypt` when encrypting) to `warehouse-backups/<state name>/<backup>.tar.enc` via `.partial` + rename, hashing the stream as written and comparing with a direct-I/O read back from the drive; writes `<backup>.tar.enc.sha256` and `<backup>.tar.enc.hmac` (HMAC of the checksum line); never overwrites a damaged archive. It makes room first if the drive is short (oldest valid archives, never the last one; else `drive too small`): `free_bytes` returns non-zero when `df` gives no number, and `make_room` then refuses the run before it writes or deletes anything (an unreadable figure is never taken for zero), and it deletes nothing when even all the deletable archives together would not make room. Every step of `copy_backup` is checked by hand (the call sits in `|| copy_rc=$?`, where errexit does not apply), and a checksum or signature file whose archive is missing is removed at the start of the next run, next to the `.partial` clean-up. The run holds the operator lock from the copy to the end (accepted: the 5-minute checker is quiet meanwhile and `operator_lock_stuck` fires at 2 h, see MONITORING.md). The restore check opens the newest archive that carries a valid signature of the backup key (an archive without one is never opened and is reported; one whose checksum matches but whose signature is from another key is reported separately, see the key-replacement step in OPERATOR_INSTALL.md): the archive is hashed first (`archive_valid`), then it needs room in `$STATE` for the archive's small files (`backup_archive_small_bytes`, which reads only the start of the archive, or takes the archive size when the tree comes before `storage.manifest`, as in an archive of the previous release) plus 256 MiB, extracts those into a private temp dir under the state with `backup_archive_extract --no-tree`, and runs `verify-restore.sh --no-storage-tree` (the photos are vouched for by the signed manifest and the hash taken while writing; they are never unpacked onto the data disk). After a run with no failure it deletes this installation's readable `.tar` archives if an encrypted one was written and passed the restore check in the run (never on a run with `WAREHOUSE_USB_BACKUP_VERIFY_RESTORE=no`; an exFAT delete does not wipe, so the run prints a note and the docs say to rotate or retire the drive), then everything but the newest `KEEP` valid archives; archives that are damaged, unsigned or signed with another key are listed and never touched. It records the result in `<state>/config/usb-backup.last` (read by `scripts/usb-backup-status.mjs` for the doctor warning, which also warns about a missing or mismatched key escrow record, and about an installation whose conf says `ENCRYPT=no` without `ENCRYPT_SET=typed`, or whose unit says `WAREHOUSE_BACKUP_ENCRYPT=0`, i.e. one that never reran `setup` after encryption became the default) and in `LAST-RESULT.txt` on the drive; a failed fresh backup still copies the newest existing one but marks the run failed and deletes nothing.
- Tests: `tests/backup-usb.test.mjs` runs every subcommand against PATH shims (`lsblk`, `findmnt`, `mount`, `umount`, `systemctl`, `udevadm`, `chown`, `id`, `getent`, `setpriv`; fixture in `tests/usb-test-helpers.mjs`, with a stand-in `df` for the free-space rules) and the fake `docker`; `tests/backup-usb-drive.test.mjs` covers what a run does with the drive's contents (restore check without photos, keep 3, foreign archives, making room, deleting readable archives, a failing run never deleting); `tests/backup-archive.test.mjs` and `tests/backup-escrow.test.mjs` cover the archive form and the key copy confirmation (the `show` test uses `script` for a terminal and skips without it). `WAREHOUSE_USB_BACKUP_ETC`, `_LIBEXEC`, `_RUN`, `_SETTLE`, `_LOCK_WAIT`, `_FRESH` and `_VERIFY_RESTORE` exist for them (`status` prints the first three when set), and so does `WAREHOUSE_USB_KEEP`. The test `df` stand-in answers for the drive and the state directory from `FAKE_DRIVE_CAP`, `FAKE_STATE_AVAIL` and `FAKE_DF_BROKEN=drive|state`.
- **Not verifiable in CI:** udev, systemd and the real mount. Before a release that touches them, on a VM with a real exFAT USB stick: `setup --enroll` (it needs `sudo` with a password prompt, so a human runs it in a real terminal unless the tester has temporary passwordless sudo; it does not start a run for the already-attached drive, and `journalctl -u 'warehouse-usb-backup@*'` says "No data available" until the first run) → re-plug → `journalctl -u 'warehouse-usb-backup@*'` shows the fresh backup, copies, read-back and verify-restore, and the drive ends unmounted → re-plug again (everything "already present") → plug an unenrolled exFAT stick (no run, still mounted by the desktop) → pull the drive mid-copy (only a `.partial` is left; the next run removes it) → `--daily` and `systemctl start warehouse-usb-backup-scan.service` with the drive attached → `uninstall`.

Manual fallback (same layout; for a host where `setup` cannot be run), as the installation user with the drive mounted by the desktop:

```bash
export WAREHOUSE_STATE_DIR=/srv/warehouse/<instance>
DRIVE="/media/$USER/<label>"            # lsblk -o NAME,TRAN,FSTYPE,LABEL,MOUNTPOINTS: TRAN usb, FSTYPE exfat
findmnt "$DRIVE"                        # must be a real mount, not a plain directory on the system disk
npm run db:backup                       # fresh backup; briefly stops write-facing services

set -euo pipefail; umask 077
source scripts/backup-key.sh; source scripts/backup-archive.sh
backup_key_load "$WAREHOUSE_STATE_DIR/config/backup.key"
DST="$DRIVE/warehouse-backups/<instance>"; mkdir -p "$DST"
n=$(ls -1 "$WAREHOUSE_STATE_DIR/backups" | grep '^warehouse-' | tail -n 1); b="$WAREHOUSE_STATE_DIR/backups/$n"   # the newest
test ! -e "$DST/$n.tar.enc"                                                                                       # never overwrite: stops if it exists
WAREHOUSE_BACKUP_KEY_FILE="$WAREHOUSE_STATE_DIR/config/backup.key" backup_authenticate "$b" false                # source intact and signed
hash=$(backup_archive_write "$b" "$DST/.$n.tar.enc.partial" encrypt); sync -f "$DST/.$n.tar.enc.partial"       # leave out `encrypt` for a readable .tar
mv "$DST/.$n.tar.enc.partial" "$DST/$n.tar.enc"; printf '%s  %s\n' "$hash" "$n.tar.enc" > "$DST/$n.tar.enc.sha256"
backup_sign_archive "$DST/$n.tar.enc" "$BACKUP_KEY"
(cd "$DST" && sha256sum -c --quiet "$n.tar.enc.sha256")

T=$(mktemp -d "$WAREHOUSE_STATE_DIR/.usb-verify.XXXXXX"); backup_archive_extract "$DST/$n.tar.enc" "$T" --no-tree   # prove the copy restores
npm run db:verify-restore -- --no-storage-tree "$T/$n"; rm -rf "$T"
udisksctl unmount -b /dev/<partition>                                  # then unplug
```

- One pax `.tar` (or `.tar.enc`) per backup keeps the 0600/0700 modes, modification times and the stored files' `user.*` attributes inside the archive (exFAT has no Unix permissions, hard links or attributes) and avoids exFAT name quirks; it is self-contained (hard links written out), so no archive depends on another and a single one restores a host. The `.sha256` file lets anyone, on any OS, check the archive.
- Write only under `warehouse-backups/<instance>/`; never touch other files on the drive, never overwrite an existing archive (a mismatching archive is a failure to investigate, not to replace), and delete only archives this installation signed and has checked (older than the newest `KEEP` valid ones, or readable ones once an encrypted one is verified) with their `.sha256` and `.hmac`.
- **Lost host: `scripts/restore-host.sh` (`npm run db:restore-host -- --state-dir NEW --yes BACKUP_DIR_OR_TAR`).** `setup.sh` on a new host mints a new identity that `scripts/restore.sh` (L58) refuses, so restore-host never runs setup. In order:
  - Needs `--backup-key FILE` (the operator's copy of `config/backup.key`); `--allow-unsigned` instead only when the key is lost (a v5 or v6 backup whose signature file was removed is refused while `--backup-key` is given). Validates everything first, creating nothing: `.tar`/`.tar.enc` against its `.sha256` and `.hmac` (an `.enc` is decrypted into the scratch directory), its entries (only `<name>/`, regular files and directories), `backup_authenticate` (checksums, signature, exact file set, and for v6 the tree), format v5 or v6, no Docker volume named `<project>_*`, migration ledger (the checkout's first `migration_count` files must reproduce the backup's `migration_fingerprint`, computed exactly like `scripts/backup-integrity.sql`), no container labelled with the project, `doctor --host-preflight`. NEW must be absent or empty, symlink-free, outside the checkout, under a parent owned by the user.
  - Builds the state in `NEW.restoring-*` and renames it: the backup's `compose.env` with only `WAREHOUSE_DB_PATH`, `WAREHOUSE_STORAGE_PATH` and `WAREHOUSE_MANIFEST_PATH` rewritten, the backup's `instance.json`, and a copy of the backup under `backups/`.
  - Runs `restore.sh --yes --relocated`. `--relocated` (internal; not combinable with `--restore-config`) compares `compose.env` ignoring only those three lines. Every in-place restore already starts from an empty cluster, and the setup SQL (auth, SMS, storage, admin, operator) only changes the `postgres` database, which the dump carries.
  - Removes the empty `*.pre-restore-*` directories.
  - Tests: `tests/restore-host.test.mjs` (stub `restore.sh` for the command's own logic; real `restore.sh` for `--relocated`). CI "Lost-host restore drill" does it for real: backup, fingerprint, `compose down`, restore-host into a different path, identical fingerprint and integrity report, `operator-api-restore.mjs`.
  - Central key file: when the backup has `central-jwks.json`, restore-host installs it as `public/central-jwks.json` (0644) and says so; when it has none but `compose.env` sets `CENTRAL_JWKS_FILE` (a backup from before backups carried the file), it exports `WAREHOUSE_CENTRAL_KEY_PENDING=yes` to `restore.sh` so that the final `doctor --local` only warns about the missing file, and adds the exact `setup.sh --operator … --central-jwks-file` rerun to the next steps. Nothing is printed for an installation that fetches its keys or has central sign-in off. `backup.sh` copies `public/central-jwks.json` (a regular file, else it refuses) and lists it in `SHA256SUMS`; `verify-restore.sh` accepts it only as a regular, checksummed file; `doctor` (`checkCentralKeyFile`) fails when the file named by `CENTRAL_JWKS_FILE` is missing or not a usable key set. Format stays v5: the file is optional and signed. Tests: `tests/restore-host.test.mjs`, `tests/backup-operator.test.mjs`, `tests/doctor.test.mjs`. `config/image-recipes.sha256` is not carried: it records host-specific image IDs, so a new host would ignore it.
  - Tunnel credential: carried when the backup has `tunnel/` (see below). restore-host copies it into `config/tunnel/`, rewrites `credentials-file:` to the new state, and prints `sudo bash scripts/tunnel.sh install-service`.
- **Tunnel credential in the state: `scripts/tunnel.sh`.**
  - `adopt --config FILE | --token-file FILE` (installation user) copies a locally managed `config.yml` plus its credentials JSON, or a dashboard token, into `config/tunnel/` (0700/0600) through a staging directory. It rewrites `credentials-file:` to the state copy.
  - `adopt` refuses: any `-----BEGIN` block (`cert.pem`, keys); an `origincert:` line; a credentials JSON whose `TunnelID` differs from `tunnel:` or that lacks `TunnelSecret`/`AccountTag`; a config whose `hostname:` lines do not include the host of `instance.json` `canonicalOrigin`; a multi-line token; an existing `config/tunnel`.
  - `install-service` (root through sudo, `SUDO_UID` non-zero, state owned by that user) writes `warehouse-<state basename>-tunnel.service`, the name the operator guide always used. It keeps a dated copy of an existing unit, then runs `daemon-reload`, `enable` and `restart`, and checks `is-active`.
  - `backup.sh` copies `config/tunnel/{config.yml,credentials.json,token}` to `tunnel/` in the backup and lists them in `SHA256SUMS`. `verify-restore.sh` accepts only those names as regular, checksummed files. In-place `restore.sh` leaves the running credential alone.
  - Tests: `tests/tunnel.test.mjs` (PATH shims for `systemctl`, `id`, `getent`; `WAREHOUSE_TUNNEL_UNIT_DIR` override, printed by `status`), plus tunnel cases in the backup, verify-restore and restore-host tests. The CI lost-host drill adopts a placeholder credential (fictional values, never run) and checks it after the restore. A real connector start is only exercised by hand.
  - Security: the credential lets its holder run a connector for the hostname, so a lost drive means replacing it (operator guide, "USB backup drive"). `cert.pem` must never be adopted.
- `scripts/data-fingerprint.sh` (read-only) prints a row count and SHA-256 per business table (including `orders`, `order_items`, `order_revisions` and `payments`) and per append-only history (`invoice_discount_history`, `invoice_zero_charge_history`, `item_price_history`), the storage catalog and the stored files (hashed inside the storage container); compare before backup and after restore. A fingerprint taken by an earlier release has fewer lines (it lacks the four order and payment tables), so it is not line-comparable with a newer one: take both on the same release. `scripts/backup-integrity.sql` (the backup's `integrity.txt`) adds `payment_count`, `order_item_count` and `order_revision_count` in a block that is printed only when migration 95 or later is in the ledger (the baseline counts as that: it contains migrations 0 to 110), so a backup from an earlier release still verifies. It excludes self-changing tables (OTPs, rate limits, idempotency keys, audit log, queues); `user_profiles` changes on sign-in, so take it before anyone uses the app again.
- VMware USB passthrough can drop a device; do not detach during a copy.

## Migration conventions

- **The baseline.** Migrations 000 to 110 are squashed into one file, `migrations/00000000000000_baseline.sql`. The old files are kept only under the git tag `migrations-pre-baseline`: read one with `git show migrations-pre-baseline:migrations/<file>`. "Migration N" in the docs and in code comments, up to 110, means that old file. Never edit the baseline. `scripts/baseline/README.md` says how it was generated and how `npm run baseline:verify` proves it is an exact squash of the chain.
- Append-only: add `migrations/<14-digit number>_<topic>.sql` with the next number (numbering continues after the baseline, so the next file is `00000000000127_<topic>.sql`) and a leading comment that says what changed and why. Never edit an applied file; the ledger stores checksums and refuses changed files. A database whose ledger names a file this release does not have (one built from the old chain) is refused too: see [Baseline reload](OPERATOR_INSTALL.md#baseline-reload).
- Run migration files only through the ledger (`scripts/migrate.sh`), never by hand. Run directly a second time (the old files, in the tag), most marker-patch migrations fail closed on their count check, but two (57 and 58) add their fragment again, because their replacement contains the marker it replaces. Write a new marker-patch migration so that each before-text is not contained in its after-text, and check it by running the file twice in a throwaway database: the second run must raise the count error.
- **A function that has a definition file is changed in that file, not in a migration.** `migrations/definitions/*.sql` holds `warehouse_security.authorize_rpc` and the RPCs that migrations 111 to 126 patched with `DO $patch$` blocks (the current text of each, with its `REVOKE`/`GRANT`). After the numbered files, the plan (`scripts/migration-plan.mjs`) applies each file whose sha256 differs from the row in `warehouse_migrations.definitions` (or has none), in name order (`00_authorize_rpc.sql` first), each in its own transaction under the same `lock_timeout`, then writes the row and sends `NOTIFY pgrst`; an unchanged file prints `Definition unchanged: <file>`. A file may hold only `CREATE OR REPLACE FUNCTION`, `COMMENT ON FUNCTION`, `GRANT`/`REVOKE ... ON FUNCTION` and `ALTER FUNCTION ... SET`/`RESET`, all about the one function of the file's `REVOKE ALL ON FUNCTION` line (no owner, rename, schema or `SECURITY` change): the plan is not built otherwise (`tests/definitions.test.mjs`). Before applying a file the plan checks that the function exists with the signature of that line and stops, naming the file, when it does not (a stale file never brings a dropped function back), and it rolls a file back that would add a second overload. A run that applied any numbered migration forgets the recorded checksums, so every file is applied again after it; the rows of removed files are deleted. A fix to a definition file can ship as a patch of the current line: cut `release/MAJOR.MINOR` from the line's latest tag, apply the file change, tag the patch there; the `release/*` guard in `ci.yml` (no numbered migration, no added, removed or renamed definition) applies to every such branch. Only a minor release that contains `migrations/definitions/` can take it. Write the whole function and its grants in the file (keep the `SET search_path`), so a change is a diff of the function; the `--through` run of the Baseline reload applies none. `tests/migrations.sh` builds a database from the numbered files alone and one with the definitions and compares their catalogs (`scripts/baseline/catalog-diff.mjs`, allow-list `tests/definitions-allowed-differences.txt`): a definition changed on purpose needs its two `^function\|<schema>\.<name>\(` lines there (schema `public` or `warehouse_security`), with the reason, and `^acl\|function\|` lines for a grant change; the same test walks that procedure. A new RPC, a signature change (a `DROP FUNCTION` of the old one), the grants of a new function, and every table, column, policy and data change stay in numbered migrations; a migration that drops or re-signs a function with a definition file changes or removes the file in the same commit, and its new `CREATE FUNCTION` is followed by `REVOKE ALL ON FUNCTION … FROM PUBLIC, anon, authenticated` in the same migration (the static test allows `REVOKE`, and only `REVOKE`, on the new signature). Other function bodies (not in `migrations/definitions/`) are still patched by a migration:
- Patch an existing function body (one without a definition file) with a `DO $$ ... $$` block that reads the current definition, counts the expected marker text, `RAISE EXCEPTION`s when the marker is missing or found more than once, and only then replaces it. A silent no-op is a bug.
- End every migration that changes the API surface with `NOTIFY pgrst, 'reload schema';` as the last statement.
- The plan (`scripts/migration-plan.mjs`) runs each file in its own transaction after `SET LOCAL lock_timeout = '10s'` and sends `NOTIFY pgrst, 'reload schema'` after its `COMMIT`; `scripts/migrate.sh` runs the plan again (three attempts, five seconds apart) when a file fails with `55P03`. Write a migration so that it holds its heaviest lock briefly: no `LOCK TABLE`, no long query between the first statement that locks a table and the end of the file. A file that builds indexes starts with `SET LOCAL maintenance_work_mem = '256MB';` (new files only; applied files are never edited).
- Never remove, rename, edit or insert before an existing file in `migrations/` (`scripts/check-migration-order.mjs`, CI job `migration-order`; `CONTRIBUTING.md`). The storage policies of `scripts/configure-storage.sql` read `goodsreceived.gr_image_url`, `dispatch.disp_image_url`, `grn_images` and `dispatch_images` columns; on an installed facility they exist when the next migration runs, so `tests/storage_policy_deps.sql` lists the `pg_depend` rows from those policies to `public` columns and `tests/migrations.sh` applies the newest migration onto a database that already has them. Change a policy first, keep the column until every facility has run the new setup, and update the list in the same commit.
- `upgrade-preflight.sh` of a release rehearses that release's migrations on a restored copy of the newest verified backup (`scripts/upgrade-rehearse.sh`, `scripts/verify-restore.sh --keep`/`--rm`); a migration that fails on existing data therefore refuses the upgrade before any change. `tests/seed/make-seed.mjs` generates the fictional facility the `seeded-upgrade` job and `tests/migrations.sh` use.
- Grant staff access only through the explicit RPC allowlist and prove each change in `tests/*.sql` with the real guarded RPCs (see `tests/staff_dispatch_invoice_access.sql`), not with a probe that cannot fail. Every function granted to `authenticated` must be classified in the table at the top of `tests/role_allowlist.sql` (staff yes/no, customer any/own/no); the test fails for a granted function it does not know and calls every refused one.

### A self-hosted runner for `operator-install`

Every CI job takes its runner from a repository variable (Settings, Secrets and variables, Actions, Variables), a JSON value such as `["self-hosted","linux","x64","warehouse-vm"]`: `operator-install` and `operator-upgrade` read `OPERATOR_INSTALL_RUNNER`, the other jobs read `CI_RUNNER`. Without the variable a job runs on `ubuntu-latest`, so a fork needs nothing; a pull request from a fork always runs on GitHub's hosted runners, whatever the variables say, so a fork's code never runs on the project's own machine. One self-hosted runner runs the jobs one after another. The job is not a required check: when the runner is offline the job waits (GitHub gives up on a job after 24 hours in the queue) and merging is not blocked. To go back to hosted runners, delete the variable.

Why: on a hosted runner about half of the job's time is image builds from scratch. On a runner that keeps Docker's build cache, the job takes about 9.5 minutes.

What the runner must provide:

- Linux x86-64 with Docker Engine and its compose and buildx plugins; the runner account is in the `docker` group. The job installs its own Node. It needs `rsync` and `attr` (`setfattr`, `getfattr`) on the runner for the backup steps (the hosted `ubuntu-latest` image has `rsync`; the job installs `attr` and `rsync` with `sudo apt-get` when `sudo` is available and otherwise stops with a message that names them), and a filesystem under `/tmp` and the runner's temp directory that keeps `user.*` extended attributes (ext4 and xfs do; some tmpfs and overlay mounts do not).
- **One job at a time on that Docker daemon.** The job publishes fixed ports on loopback (18000 for the gateway and 3000 for the renderer golden-file check), creates the network `10.233.245.0/24` and writes fixed paths under `/tmp`.
- **A cleanup after every job and before the runner starts**, because a hosted runner is a new machine every time and this one is not: remove all containers, all volumes and unused networks, the paths `/tmp/warehouse-ci-*`, and the contents of the runner's temporary directory (`_work/_temp`). The state directory in there holds files owned by the containers' users, so removing it needs root; the runner's job-completed hook (`ACTIONS_RUNNER_HOOK_JOB_COMPLETED`) is the place. Keep the images and the build cache: they are the point.
- Enough disk for the images and the cache (tens of gigabytes), with pruning only when the disk fills.

Security, which decides where such a runner may live:

- This repository is public and the job needs Docker, which is as good as root on the runner. Code from a pull request, or from the install script of a dependency, runs there. Use a dedicated machine that holds nothing of value (no credentials, no keys, no other services), that cannot reach your other machines, and that you can delete and rebuild.
- Require approval before workflows run for pull requests from all outside contributors (Settings, Actions, General). Pull requests opened by Dependabot come from inside the repository and need no approval.
- Keep the workflow token read-only and give the repository no Actions secrets that this job could read. Never point a release or deployment job at this runner.
