# Contributor guide

Orientation for changing this backend. Operator instructions are in [OPERATOR_INSTALL.md](OPERATOR_INSTALL.md); the README quickstart is the entry point for a new installation.

## Repository layout

- `setup.sh`, `start.sh`, `stop.sh`, `rotate-keys.sh` — operator commands; each takes the per-state lock (`scripts/operator-lock.sh`) before touching Docker. `health-check.sh` keeps its name but takes no lock: it is a thin wrapper over `node scripts/watch.mjs health` (the one health check, also used by `doctor --local`) that adds diagnostics.
- `scripts/` — `configure.mjs` (state and config generation), `doctor.mjs` (host preflight, local and external checks), `migrate.sh` + `migration-plan.mjs` (checksummed ledger), `backup.sh` / `verify-restore.sh` / `restore.sh`, `backup-usb.sh` (automatic copy to an enrolled USB drive; see below) and `usb-backup-status.mjs` (its doctor warning), `restore-host.sh` (rebuild a lost host from a backup), `tunnel.sh` (tunnel credential in the state, its systemd unit), `data-fingerprint.sh` (before/after restore comparison), `rotate-keys.mjs` + `keys.mjs`, `compose.sh` (project-owned Compose wrapper), `check-mobile-contract.mjs`. The CI-only drivers (`gateway-smoke.mjs`, `gateway-dns-check.sh`, `load-smoke.mjs`, `recovery-check.sh`, `cups-check.sh`, `sensor-bridge-check.sh`, `pooler-check.sh`) live in `tests/`, with their `npm run test:*` names.
- `migrations/` — numbered SQL applied in order. `functions/` — Deno edge functions. `docker/` — Compose files and digest-pinned image recipes; `docker/sensor-bridge/` is the Python Tapo sensor bridge, licensed GPL-3.0-or-later (its own `LICENSE`): the one directory of original code that is not MIT. `deploy/` — the cloudflared config example.
- `scripts/set-capability.mjs <sensors|printing> <on|off>` — edits one flag of `<state>/public/instance.json` atomically (the app's capabilities); afterwards restart `functions` and take a backup (`db:restore` refuses a backup with a different manifest).
- `tests/` — node tests (`*.test.mjs`), SQL tests run by `tests/migrations.sh`, and HTTP drivers for a live instance. The CI install job runs four of them: `operator-api-core.mjs`, `operator-api-final.mjs`, `operator-api-rotation.mjs` (`npm run test:rotation`) and `operator-api-restore.mjs`, all through `operator-fixture.mjs`. Pending, rejected and disabled sign-in, OTP expiry and staff documents are covered in CI by the SQL tests.

## Running checks

- `npm ci && npm test` — node unit tests; no Docker, no network.
- `bash tests/migrations.sh` — applies every migration twice to a disposable, network-isolated container of the database image (`postgres:18`, the pin printed by `scripts/db-image.sh`) (the second pass must skip unchanged files) and runs the SQL tests. Needs Docker.
- Shell syntax is checked by `npm test` (`tests/shell-syntax.test.mjs`); there is no separate CI step.
- `node scripts/check-mobile-contract.mjs <mobile checkout>` — static name inventory against the app (needs the app's `node_modules`); the pin it runs against is described in [CONTRIBUTING.md](../CONTRIBUTING.md#mobile-companion-pin-mobile_ref). The `contract` job also runs `tests/rpc-callers.test.mjs` with `MOBILE_CHECKOUT` set, which compares the app's RPC names with `tests/rpc_callers_exist.sql`.
- Sensor bridge: `cd docker/sensor-bridge && python3 -m unittest discover -s tests -t .` (Python 3.15 with `requirements.txt` installed; CI job `bridge`), and `npm run test:sensors` on an installed state (builds the image; `--check-config` must exit 0 with fictional values and 78 without; the unit tests run inside the image). Without `docker/sensor-bridge/Dockerfile` it fails.
- Everything else (`npm run test:gateway`, `test:rotation`, `test:anon-timeout` (the 3 s limit of `anon` through PostgREST), `db:backup`, ...) needs an installed operator state; CI exercises them in the `operator-install` job.

## Backup key, signing and the restore verifier

- `scripts/backup-key.sh` (sourced) is the one place for the key and the crypto. The key is `<state>/config/backup.key` (64 hex, 0600), created by `configure.mjs` (fresh setup, and a rerun on a state without one) or by the first `backup.sh`. It is never copied into a backup. `WAREHOUSE_BACKUP_KEY_FILE` overrides the path for verification.
- `backup_hmac` is HMAC-SHA256 built from `sha256sum` and shell builtins, so the key never appears in a process argument list (`openssl dgst -hmac KEY` would show it in `ps`) and the script does not need Node, which is not on the PATH of the systemd unit. The tests sign fixtures with Node's `crypto` (`tests/backup-test-helpers.mjs` `hmacHex`), so the two implementations check each other. Every use has its own label (`warehouse-backup-manifest-v1`, `-archive-v1`, `-encryption-v1`, `warehouse-usb-enrolment-v1`).
- Format **v5** = v4 plus `SHA256SUMS.hmac`. `backup_authenticate DIR ALLOW` runs before anything in a backup is parsed: `sha256sum -c`, then the HMAC, then "the files present are exactly the files listed". A present-but-wrong signature is refused even with `--allow-unsigned`; a missing signature or a missing key is accepted only with it, with a banner on stderr. The flag is only for a lost key. `verify-restore.sh`, `restore.sh` and `restore-host.sh` accept format v5 only and refuse any other label ("Refusing: backup format 'warehouse-backup-vN' is no longer supported; take a new backup with this version") before the signature is checked; the label is read before it is authenticated, which is safe because a refusal trusts nothing. A **v5** backup (`format=` in `metadata.txt`) whose signature file is missing is refused even with the flag while the key (`backup_key_path`) exists, before any checksum is run. The rule is in `backup_authenticate`.
- `verify-restore.sh` creates its databases from **template0**. A session attached to template1 right after start-up failed `createdb -T template1` in CI on 2026-10-09 ("source database template1 is being accessed by other users"); the likely owner was a background-worker launcher of the earlier database image (the official image has none). template0 accepts no connections, so the race cannot occur; `restore.sh` uses it for the same reason. The dump is self-contained, so nothing from template1 is needed.
- The verifier sizes its data directory from the dumps (factor 10, WAL allowance, floor 768 MiB), uses tmpfs when `MemAvailable` covers it and otherwise a directory under the state that the image itself empties afterwards (PostgreSQL's files belong to the container's user). On failure it saves `docker logs`, the container state and `pg_stat_activity` under `<state>/diagnostics/` before removing the container.
- Real-container coverage without an installed stack: `tests/verify-restore-drill.sh`, run at the end of `tests/migrations.sh`, dumps the migration test database into a signed v5 fixture and runs the verifier twice, once with a session held on template1 and once disk-backed. `WAREHOUSE_DRILL_KEEP=1` keeps the fixture.
- **Not verified on real containers:** any restore from an encrypted archive.
- Database passwords are one per login since 2026-10-18 (TW-BE-002; [CONTAINER_SECURITY.md](CONTAINER_SECURITY.md#database-passwords-one-per-login)). The list of service logins is `DB_ROLE_LOGINS` in `scripts/db-roles.mjs`. `SECRET_KEY_BASE` and `VAULT_ENC_KEY` exist only after `bash scripts/pooler.sh on` and have no rotation script; the operator guide says so.

## USB backup drive

The operator attaches an **existing exFAT USB drive** and the system does the rest. exFAT because the install may run on Linux or in the Linux VM of a Windows host, and a restore must work on either; the drive is never partitioned or formatted, so existing files on it stay untouched. Archives are signed with the backup key (next section) and are encrypted only when the operator runs `setup --encrypt` (`WAREHOUSE_BACKUP_ENCRYPT=1` in the unit): unencrypted, anyone holding the drive can read every credential in `compose.env`, so the drive is kept locked away and a lost drive means `rotate-keys.sh --yes`. Encryption is opt-in because a lost key makes the archives unrecoverable and the encrypted lost-host path has only stub coverage so far. A drive kept on site does not close the off-host custody gate in [PRODUCTION_DEPENDENCIES.md](PRODUCTION_DEPENDENCIES.md); rotating it to another location does.

`scripts/backup-usb.sh` automates it. Layout and trust boundaries:

- **Root, installed once** by `sudo bash scripts/backup-usb.sh setup --state DIR --enroll /dev/sdX1`: copies the script itself to `/usr/local/libexec/warehouse-usb-backup` (root-owned, so root never runs code from the user-writable checkout; setup refuses a group/world-writable script), writes `/etc/warehouse-usb-backup.conf` (state, checkout, user, uid/gid, options), `/etc/warehouse-usb-backup.drives` (root-only, 0600: one `<filesystem UUID> <partition UUID>` line per enrolled drive), a udev rule with one line per enrolled UUID (`ID_BUS==usb`, `ID_FS_TYPE==exfat`) that adds `SYSTEMD_WANTS=warehouse-usb-backup@%k.service`, the template unit, and a scan service + daily timer (enabled only with `--daily`). A rerun keeps `DAILY`, `FRESH_BACKUP` and `ENCRYPT` from the existing conf unless an option names another value (`--no-daily`, `--fresh-backup`, `--no-encrypt`). `enroll`, `uninstall` and `status` complete the set.
- **The unit** runs `ExecStartPre=+helper mount %I` (root: re-checks USB/exFAT/enrolled, waits a few seconds for a desktop automount and uses it, otherwise mounts privately under `/run/warehouse-usb-backup/` with `uid/gid`, `fmask=0177`, `dmask=0077`, `nosuid,nodev,noexec`), then `ExecStart=bash <checkout>/scripts/backup-usb.sh run --device %I` **as the installation user**, then `ExecStopPost=+helper unmount %I` (always, also after a failure: `sync`, unmount every mount of the enrolled drive). The checkout path is baked into the unit: run setup again after moving or updating the checkout (`status` compares the helper with the checkout).
- **Enrolment** is not the exFAT volume serial (32 bits, settable with `mkfs.exfat -i`). `enroll` (root, from the checkout) writes `warehouse-backups/.drive-enrolment` onto the drive: `hmac=` is `backup_hmac(key, "warehouse-usb-enrolment-v1", "<fs uuid>\n<partuuid>\n<instance id>\n")`. `mount` (root helper) accepts only an exact `UUID PARTUUID` line of the root-only list; `run` cannot read that list and instead recomputes the marker HMAC for the drive it sees, before the fresh backup. A bare-serial line left by an earlier release is refused with a re-enrol message; because `run` never starts for it, the helper records that refusal itself in `usb-backup.last` (through `setpriv`, as the installation user, with the internal `refused` subcommand), and `setup` does the same for every such line it finds, so `status` and doctor show it at once. The udev rule still names the serial (world-readable): it only starts the unit, and a forged drive then fails the marker check with nothing copied.
- **`run`** (installation user): refuses root, unenrolled/non-USB/non-exFAT/read-only drives, an unmounted drive, a mount on the data device, and a folder whose `.instance-id` belongs to another instance. It waits up to 15 minutes for the operator lock, runs `scripts/backup.sh` (which takes the lock itself), then holds the lock while it writes `warehouse-backups/<state name>/<backup>.tar` via `.partial` + rename, hashing the stream as written and comparing with a direct-I/O read back from the drive; writes `<backup>.tar.sha256` and `<backup>.tar.hmac` (HMAC of the checksum line; with encryption the stream passes `backup_encrypt` and the names end in `.tar.enc`); never overwrites or deletes; extracts the newest archive that carries a valid signature of the backup key into a private temp dir under the state and runs `verify-restore.sh` on it (an archive without one is never unpacked and is reported; one whose checksum matches but whose signature is from another key is reported separately, see the key-replacement step in OPERATOR_INSTALL.md). It records the result in `<state>/config/usb-backup.last` (read by `scripts/usb-backup-status.mjs` for the doctor warning) and in `LAST-RESULT.txt` on the drive; a failed fresh backup still copies the existing ones but marks the run failed.
- Tests: `tests/backup-usb.test.mjs` runs every subcommand against PATH shims (`lsblk`, `findmnt`, `mount`, `umount`, `systemctl`, `udevadm`, `chown`, `id`, `getent`, `setpriv`) and the fake `docker`; `WAREHOUSE_USB_BACKUP_ETC`, `_LIBEXEC`, `_RUN`, `_SETTLE`, `_LOCK_WAIT`, `_FRESH` and `_VERIFY_RESTORE` exist for them (`status` prints the first three when set).
- **Not verifiable in CI:** udev, systemd and the real mount. Before a release that touches them, on a VM with a real exFAT USB stick: `setup --enroll` (it needs `sudo` with a password prompt, so a human runs it in a real terminal unless the tester has temporary passwordless sudo; it does not start a run for the already-attached drive, and `journalctl -u 'warehouse-usb-backup@*'` says "No data available" until the first run) → re-plug → `journalctl -u 'warehouse-usb-backup@*'` shows the fresh backup, copies, read-back and verify-restore, and the drive ends unmounted → re-plug again (everything "already present") → plug an unenrolled exFAT stick (no run, still mounted by the desktop) → pull the drive mid-copy (only a `.partial` is left; the next run removes it) → `--daily` and `systemctl start warehouse-usb-backup-scan.service` with the drive attached → `uninstall`.

Manual fallback (same layout; for a host where `setup` cannot be run), as the installation user with the drive mounted by the desktop:

```bash
export WAREHOUSE_STATE_DIR=/srv/warehouse/<instance>
DRIVE="/media/$USER/<label>"            # lsblk -o NAME,TRAN,FSTYPE,LABEL,MOUNTPOINTS: TRAN usb, FSTYPE exfat
findmnt "$DRIVE"                        # must be a real mount, not a plain directory on the system disk
npm run db:backup                       # fresh backup; briefly stops write-facing services

set -euo pipefail; umask 077
SRC="$WAREHOUSE_STATE_DIR/backups"; DST="$DRIVE/warehouse-backups/<instance>"; mkdir -p "$DST"
for b in "$SRC"/warehouse-*; do n=$(basename "$b")
  [ -e "$DST/$n.tar" ] && { (cd "$DST" && sha256sum -c --quiet "$n.tar.sha256"); continue; }   # never overwrite
  (cd "$b" && sha256sum -c --quiet SHA256SUMS)                                                   # source intact
  tar -C "$SRC" -cf "$DST/.$n.tar.partial" "$n"; sync -f "$DST/.$n.tar.partial"
  (cd "$DST" && sha256sum ".$n.tar.partial" | sed "s/\.$n\.tar\.partial/$n.tar/" > ".$n.sha.partial")
  mv "$DST/.$n.tar.partial" "$DST/$n.tar"; mv "$DST/.$n.sha.partial" "$DST/$n.tar.sha256"
  (cd "$DST" && sha256sum -c --quiet "$n.tar.sha256")
done; sync

T=$(mktemp -d); tar -C "$T" -xf "$DST/<newest>.tar"                    # prove the copy restores
npm run db:verify-restore -- "$T/<newest>"; rm -rf "$T"
udisksctl unmount -b /dev/<partition>                                  # then unplug
```

- One `.tar` per backup keeps the 0600/0700 modes inside the archive (exFAT has no Unix permissions) and avoids exFAT name and attribute quirks. The `.tar.sha256` file lets anyone, on any OS, check the archive.
- Write only under `warehouse-backups/<instance>/`; never touch other files on the drive, never delete or overwrite an existing archive (a mismatching archive is a failure to investigate, not to replace).
- **Lost host: `scripts/restore-host.sh` (`npm run db:restore-host -- --state-dir NEW --yes BACKUP_DIR_OR_TAR`).** `setup.sh` on a new host mints a new identity that `scripts/restore.sh` (L58) refuses, so restore-host never runs setup. In order:
  - Needs `--backup-key FILE` (the operator's copy of `config/backup.key`); `--allow-unsigned` instead only when the key is lost (a v5 backup whose signature file was removed is refused while `--backup-key` is given). Validates everything first, creating nothing: `.tar`/`.tar.enc` against its `.sha256` and `.hmac` (an `.enc` is decrypted into the scratch directory), its entries (only `<name>/`, regular files and directories), `backup_authenticate` (checksums, signature, exact file set), format v5, no Docker volume named `<project>_*`, migration ledger (the checkout's first `migration_count` files must reproduce the backup's `migration_fingerprint`, computed exactly like `scripts/backup-integrity.sql`), no container labelled with the project, `doctor --host-preflight`. NEW must be absent or empty, symlink-free, outside the checkout, under a parent owned by the user.
  - Builds the state in `NEW.restoring-*` and renames it: the backup's `compose.env` with only `WAREHOUSE_DB_PATH`, `WAREHOUSE_STORAGE_PATH` and `WAREHOUSE_MANIFEST_PATH` rewritten, the backup's `instance.json`, and a copy of the backup under `backups/`.
  - Runs `restore.sh --yes --relocated`. `--relocated` (internal; not combinable with `--restore-config`) compares `compose.env` ignoring only those three lines. Every in-place restore already starts from an empty cluster, and the setup SQL (auth, SMS, storage, admin, operator) only changes the `postgres` database, which the dump carries.
  - Removes the empty `*.pre-restore-*` directories.
  - Tests: `tests/restore-host.test.mjs` (stub `restore.sh` for the command's own logic; real `restore.sh` for `--relocated`). CI "Lost-host restore drill" does it for real: backup, fingerprint, `compose down`, restore-host into a different path, identical fingerprint and integrity report, `operator-api-restore.mjs`.
  - Central key file: when the backup has `central-jwks.json`, restore-host installs it as `public/central-jwks.json` (0644) and says so; when it has none but `compose.env` sets `CENTRAL_JWKS_FILE` (a backup from before backups carried the file), it exports `WAREHOUSE_CENTRAL_KEY_PENDING=yes` to `restore.sh` so that the final `doctor --local` only warns about the missing file, and adds the exact `setup.sh --operator … --central-jwks-file` rerun to the next steps. Nothing is printed for an installation that fetches its keys or has central sign-in off. `backup.sh` copies `public/central-jwks.json` (a regular file, else it refuses) and lists it in `SHA256SUMS`; `verify-restore.sh` accepts it only as a regular, checksummed file; `doctor` (`checkCentralKeyFile`) fails when the file named by `CENTRAL_JWKS_FILE` is missing or not a usable key set. Format stays v5: the file is optional and signed. Tests: `tests/restore-host.test.mjs`, `tests/backup-operator.test.mjs`, `tests/doctor.test.mjs`. `config/image-recipes.sha256` is not carried: it records host-specific image IDs, so a new host would ignore it.
  - Tunnel credential: carried when the backup has `tunnel/` (see below). restore-host copies it into `config/tunnel/`, rewrites `credentials-file:` to the new state, and prints `sudo bash scripts/tunnel.sh install-service`.
- **Tunnel credential in the state: `scripts/tunnel.sh`.**
  - `adopt --config FILE | --token-file FILE` (installation user) copies a locally managed `config.yml` plus its credentials JSON, or a dashboard token, into `config/tunnel/` (0700/0600) through a staging directory. It rewrites `credentials-file:` to the state copy.
  - `adopt` refuses: any `-----BEGIN` block (`cert.pem`, keys); an `origincert:` line; a credentials JSON whose `TunnelID` differs from `tunnel:` or that lacks `TunnelSecret`/`AccountTag`; a config whose `hostname:` lines do not include the host of `instance.json` `canonicalOrigin`; a multi-line token; an existing `config/tunnel`.
  - `install-service` (root through sudo, `SUDO_UID` non-zero, state owned by that user) writes `warehouse-<state basename>-tunnel.service`, the name the operator guide always used. It keeps a dated copy of an existing unit, then runs `daemon-reload`, `enable` and `restart`, and checks `is-active`.
  - `backup.sh` copies `config/tunnel/{config.yml,credentials.json,token}` to `tunnel/` in the backup and lists them in `SHA256SUMS`. `verify-restore.sh` accepts only those names as regular, checksummed files. In-place `restore.sh` leaves the running credential alone.
  - Tests: `tests/tunnel.test.mjs` (PATH shims for `systemctl`, `id`, `getent`; `WAREHOUSE_TUNNEL_UNIT_DIR` override, printed by `status`), plus tunnel cases in the backup, verify-restore and restore-host tests. The CI lost-host drill adopts a placeholder credential (fictional values, never run) and checks it after the restore. A real connector start is only exercised by hand.
  - Security: the credential lets its holder run a connector for the hostname, so a lost drive means replacing it (operator guide, "USB backup drive"). `cert.pem` must never be adopted.
- `scripts/data-fingerprint.sh` (read-only) prints a row count and SHA-256 per business table (including `orders`, `order_items`, `order_revisions` and `payments`) and per append-only history (`invoice_discount_history`, `invoice_zero_charge_history`, `item_price_history`), the storage catalog and the stored files (hashed inside the storage container); compare before backup and after restore. A fingerprint taken by an earlier release has fewer lines (it lacks the four order and payment tables), so it is not line-comparable with a newer one: take both on the same release. `scripts/backup-integrity.sql` (the backup's `integrity.txt`) adds `payment_count`, `order_item_count` and `order_revision_count` in a block that is printed only when migration 95 or later is in the ledger (the baseline counts as that: it contains migrations 0 to 110), so a backup from an earlier release still verifies. It excludes self-changing tables (OTPs, rate limits, idempotency keys, audit log, queues); `user_profiles` changes on sign-in, so take it before anyone uses the app again.
- VMware USB passthrough can drop a device; do not detach during a copy.

## Migration conventions

- **The baseline.** Migrations 000 to 110 are squashed into one file, `migrations/00000000000000_baseline.sql`. The old files are kept only under the git tag `migrations-pre-baseline`: read one with `git show migrations-pre-baseline:migrations/<file>`. "Migration N" in the docs and in code comments, up to 110, means that old file. Never edit the baseline. `scripts/baseline/README.md` says how it was generated and how `npm run baseline:verify` proves it is an exact squash of the chain.
- Append-only: add `migrations/<14-digit number>_<topic>.sql` with the next number (numbering continues after the baseline, so the next file is `00000000000127_<topic>.sql`) and a leading comment that says what changed and why. Never edit an applied file; the ledger stores checksums and refuses changed files. A database whose ledger names a file this release does not have (one built from the old chain) is refused too: see [Baseline reload](OPERATOR_INSTALL.md#baseline-reload).
- Run migration files only through the ledger (`scripts/migrate.sh`), never by hand. Run directly a second time (the old files, in the tag), most marker-patch migrations fail closed on their count check, but two (57 and 58) add their fragment again, because their replacement contains the marker it replaces. Write a new marker-patch migration so that each before-text is not contained in its after-text, and check it by running the file twice in a throwaway database: the second run must raise the count error.
- Patch an existing function body with a `DO $$ ... $$` block that reads the current definition, counts the expected marker text, `RAISE EXCEPTION`s when the marker is missing or found more than once, and only then replaces it. A silent no-op is a bug.
- End every migration that changes the API surface with `NOTIFY pgrst, 'reload schema';` as the last statement.
- Grant staff access only through the explicit RPC allowlist and prove each change in `tests/*.sql` with the real guarded RPCs (see `tests/staff_dispatch_invoice_access.sql`), not with a probe that cannot fail. Every function granted to `authenticated` must be classified in the table at the top of `tests/role_allowlist.sql` (staff yes/no, customer any/own/no); the test fails for a granted function it does not know and calls every refused one.

### A self-hosted runner for `operator-install`

Every CI job takes its runner from a repository variable (Settings, Secrets and variables, Actions, Variables), a JSON value such as `["self-hosted","linux","x64","warehouse-vm"]`: `operator-install` reads `OPERATOR_INSTALL_RUNNER`, the other jobs read `CI_RUNNER`. Without the variable a job runs on `ubuntu-latest`, so a fork needs nothing; a pull request from a fork always runs on GitHub's hosted runners, whatever the variables say, so a fork's code never runs on the project's own machine. One self-hosted runner runs the jobs one after another. The job is not a required check: when the runner is offline the job waits (GitHub gives up on a job after 24 hours in the queue) and merging is not blocked. To go back to hosted runners, delete the variable.

Why: on a hosted runner about half of the job's time is image builds from scratch. On a runner that keeps Docker's build cache, the job takes about 9.5 minutes.

What the runner must provide:

- Linux x86-64 with Docker Engine and its compose and buildx plugins; the runner account is in the `docker` group. The job uses no `sudo` and installs its own Node.
- **One job at a time on that Docker daemon.** The job publishes fixed ports on loopback (18000 for the gateway and 3000 for the renderer golden-file check), creates the network `10.233.245.0/24` and writes fixed paths under `/tmp`.
- **A cleanup after every job and before the runner starts**, because a hosted runner is a new machine every time and this one is not: remove all containers, all volumes and unused networks, the paths `/tmp/warehouse-ci-*`, and the contents of the runner's temporary directory (`_work/_temp`). The state directory in there holds files owned by the containers' users, so removing it needs root; the runner's job-completed hook (`ACTIONS_RUNNER_HOOK_JOB_COMPLETED`) is the place. Keep the images and the build cache: they are the point.
- Enough disk for the images and the cache (tens of gigabytes), with pruning only when the disk fills.

Security, which decides where such a runner may live:

- This repository is public and the job needs Docker, which is as good as root on the runner. Code from a pull request, or from the install script of a dependency, runs there. Use a dedicated machine that holds nothing of value (no credentials, no keys, no other services), that cannot reach your other machines, and that you can delete and rebuild.
- Require approval before workflows run for pull requests from all outside contributors (Settings, Actions, General). Pull requests opened by Dependabot come from inside the repository and need no approval.
- Keep the workflow token read-only and give the repository no Actions secrets that this job could read. Never point a release or deployment job at this runner.
