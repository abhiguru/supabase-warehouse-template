The current canonical [Haskell advisory HSEC-2026-0007](https://github.com/haskell/security-advisories/blob/main/advisories/published/2026/HSEC-2026-0007.md) rates the `aeson` memory-exhaustion issue HIGH (CVSS 3.1 vector `AV:N/AC:L/PR:N/UI:N/S:U/C:N/I:N/A:H`) and marks versions before **2.2.5.1** affected. The fix first shipped in 2.3.0.0 and was backported to 2.2.5.1. The advisory separately lists `text-iso8601` versions before **0.1.1.2**; its unit ID was not visible in any of the six stripped binaries inspected. That absence does not establish that the library or vulnerable behavior is absent.

The v14.17/v14.18 arm64 binaries are dynamically linked on Ubuntu; the corresponding amd64 binaries are static. Both v16.3 binaries are static. `strings` extraction is partial: even GHC `base` is missing from its output. It cannot establish a complete linked-component inventory or a passing vulnerability assessment. Trivy 0.74.0 reports no package results for the deployed static amd64 image, and its documented language coverage does not list Haskell. The existing fail-closed validator must continue rejecting zero-package PostgREST scans.

Upstream v14.17 uses `nix-build -A postgrestStatic` and `nix-build -A docker.image` from a pinned `flake.lock`; `nix/static.nix` builds with `pkgsStatic.haskell.packages.native-bignum`, and the Docker image copies the static output. A remedial source build would need an updated pinned Haskell/native dependency graph, build-graph evidence tied to the exact resulting binary and per-platform image digest, OSV/Hackage plus native-component assessment, warehouse API regressions, and affected physical-iPhone retest before merge. A Nix runtime-closure query alone would omit libraries statically linked into the executable. No Nix build was started on this shared host.
